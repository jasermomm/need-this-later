# Enable encrypted sync with Supabase

Need This Later works without an account or server. Everything stays in Local Mode until you choose to enable encrypted sync.

Supabase is used only to move encrypted records between your devices. Notes, URLs, filenames, and attachment contents are encrypted on your device before upload. Supabase can still see limited metadata such as your account ID, opaque record IDs, timestamps, object sizes, and access patterns.

## Choose the easiest setup

| What you want | Recommended route |
| --- | --- |
| A hosted sync server with no terminal commands | [Dashboard setup](#option-a-supabase-dashboard-no-terminal) |
| A repeatable hosted setup using terminal commands | [Hosted CLI setup](#option-b-hosted-project-with-the-cli) |
| A completely local development server on your computer | [Local CLI and Docker](#option-c-local-supabase-with-docker) |

Most people should choose **Option A**. You do not need to deploy a separate copy of the Need This Later website: the public PWA can connect to your Supabase project from its Settings screen.

## Before you start

You need:

- a free [Supabase account](https://supabase.com/dashboard);
- an email address for the account you will create inside Need This Later;
- about 10 minutes;
- a safe place for the recovery key generated by Need This Later.

Two passwords are involved and they have different jobs:

- **Account password:** Supabase uses this to sign you in.
- **Vault password:** Need This Later uses this on your device to unlock your encryption key. Supabase never receives it.

Use different passwords, each at least 10 characters long. Losing the vault password and recovery key can make the encrypted data impossible to recover.

> [!CAUTION]
> Use only a public **publishable key** (`sb_publishable_...`) or the older public **anon key**. Never paste a secret key, `service_role` key, database password, personal access token, or management token into the app, an environment file, GitHub Actions, or a browser extension.

## Option A: Supabase Dashboard (no terminal)

### A1. Create the project

1. Open the [Supabase Dashboard](https://supabase.com/dashboard) and sign in.
2. Choose **New project**.
3. Select your organization.
4. Enter a name such as `Need This Later`.
5. Generate a strong database password and save it in a password manager. This is an administrator password; it does **not** go into Need This Later.
6. Choose a region close to you and create the project.
7. Wait until the project reports that it is ready.

### A2. Install the encrypted-sync database schema

1. Open the included [`20260808000000_encrypted_sync.sql`](../supabase/migrations/20260808000000_encrypted_sync.sql) file.
2. On GitHub, choose **Raw**, then select and copy the entire file.
3. Return to Supabase and open **SQL Editor** in the left sidebar.
4. Choose **New query**, paste the copied SQL, and choose **Run**.
5. A successful run normally says `Success. No rows returned`.

Confirm the result in the Dashboard:

- **Table Editor** contains `vault_headers` and `encrypted_items`.
- **Storage** contains an `encrypted-attachments` bucket.
- The attachment bucket is marked private, not public.

The SQL enables Row Level Security and creates policies so an authenticated user can access only rows and objects under their own account ID. Do not disable RLS or make the bucket public to work around an error.

Run the SQL only once on a new project. An `already exists` error usually means the schema was already installed. If the first run stopped on another error, copy the error before changing anything and use the [troubleshooting section](#troubleshooting).

### A3. Configure email and password sign-in

1. Open **Authentication** in Supabase.
2. Open **Providers** or **Sign In / Providers**, then select **Email**.
3. Make sure email/password sign-up is enabled.
4. Set the minimum password length to at least 10 characters if that option is available in your plan/settings.
5. Open **URL Configuration**.
6. Set **Site URL** to:

   ```text
   https://jasermomm.github.io/need-this-later/
   ```

7. Add the same URL to the allowed redirect URLs. Add `http://localhost:3000` only if you also run the app locally.

Hosted Supabase projects normally require email confirmation. Leaving confirmation enabled is recommended for an Internet-facing project. The first **Create encrypted vault** attempt will create the account and tell you to check your email. Open the confirmation message, confirm the address, return to the app, select **Sign in**, and continue with the same account and vault passwords.

For a private test project, you may disable **Confirm email** in the Email provider settings. The vault will then be created immediately. Do not disable it casually for a public multi-user deployment.

### A4. Copy the two public connection values

1. Choose **Connect** near the top of the project Dashboard. If it is not visible, open **Project Settings → API Keys**.
2. Copy the **Project URL**, which looks like:

   ```text
   https://abcdefghijk.supabase.co
   ```

3. Copy the **Publishable key**, which starts with `sb_publishable_`.

An older project may show a long JWT named **anon public** instead. That key also works. Do not copy a secret or `service_role` key.

### A5. Turn on sync in the website

1. Open [Need This Later](https://jasermomm.github.io/need-this-later/).
2. Choose the gear icon to open **Settings**.
3. Find **Encrypted sync** and expand **Sync server**.
4. Paste the Project URL into **Supabase URL**.
5. Paste the publishable or legacy anon key into **Publishable or legacy anon key**.
6. Select **Create account**.
7. Enter your email, Supabase account password, and separate vault password.
8. Choose **Create encrypted vault**.
9. If email confirmation is enabled, confirm the email, return to this screen, select **Sign in**, enter the same values, and choose **Unlock encrypted vault**.
10. Download or copy the recovery key. Store it somewhere safe and offline if possible.
11. Check **I stored this key somewhere safe**, then choose **Finish & sync**.

The status should finish with **Up to date**. Create a harmless test note, choose **Sync now**, and confirm the sent count changes.

To add another device, enter the same Supabase URL, public key, email, account password, and vault password. Use **Sign in**, not **Create account**. The browser extension must connect to a vault that has already been created in the web app.

## Option B: Hosted project with the CLI

This route applies the same checked-in migration reproducibly. It is intended for people comfortable copying commands one line at a time.

### B1. Install the prerequisites

Install [Git](https://git-scm.com/downloads) and [Node.js 22 or newer](https://nodejs.org/). Then open Terminal, PowerShell, or Command Prompt and run:

```bash
git clone https://github.com/jasermomm/need-this-later.git
cd need-this-later
npx --yes supabase@latest --version
```

The last command downloads the current Supabase CLI for this command only. Do not use `npm install -g supabase`.

Create a hosted project in the Supabase Dashboard as described in [A1](#a1-create-the-project). Project creation asks for billing/region choices and an administrator password, so the Dashboard is the clearest and safest place for that step.

### B2. Sign in and link the correct project

```bash
npx --yes supabase@latest login
npx --yes supabase@latest projects list
```

Copy the **Reference ID** for the intended project, then replace `YOUR_PROJECT_REF` below:

```bash
npx --yes supabase@latest link --project-ref YOUR_PROJECT_REF
```

The CLI may ask for the database password created in A1. It can save that password in the operating system's credential storage. Do not put the password directly in a command because commands can remain in shell history.

### B3. Preview, apply, and test the migration

Preview first. This makes no database changes:

```bash
npx --yes supabase@latest db push --dry-run
```

The output should list `20260808000000_encrypted_sync.sql`. Apply it:

```bash
npx --yes supabase@latest db push
```

Run the included account-isolation checks inside a transaction that rolls back afterward:

```bash
npx --yes supabase@latest test db --linked supabase/tests/rls.sql
```

All eight pgTAP checks should pass.

> [!WARNING]
> Never run `supabase db reset --linked` against a real project. It destroys the linked remote database. `db push` applies only pending migrations and is the correct production command.

### B4. Get the public key and finish setup

List the project's API keys without revealing secret keys:

```bash
npx --yes supabase@latest projects api-keys --project-ref YOUR_PROJECT_REF
```

Use the publishable key or legacy anon key. For a hosted Supabase project, the URL is normally `https://YOUR_PROJECT_REF.supabase.co`.

Configure Authentication as described in [A3](#a3-configure-email-and-password-sign-in), then follow [A5](#a5-turn-on-sync-in-the-website). The CLI migration and Dashboard SQL produce the same schema; choose one method for the initial installation instead of applying both.

## Option C: Local Supabase with Docker

This route is for development and private testing on one computer or trusted local network. It requires Docker Desktop or another Docker-compatible runtime.

1. Install and start [Docker Desktop](https://www.docker.com/products/docker-desktop/).
2. Clone the repository and enter its folder as shown in B1.
3. Run:

   ```bash
   npx --yes supabase@latest start
   npx --yes supabase@latest db reset
   npx --yes supabase@latest test db supabase/tests/rls.sql
   npx --yes supabase@latest status
   ```

4. From the `status` output, copy the **API URL** and public **anon key**.
5. In another terminal, start the local app:

   ```bash
   npm ci
   npm run dev
   ```

6. Open the exact local URL printed by the development server and enter the local API URL/key under **Settings → Encrypted sync → Sync server**.

The public GitHub Pages site uses HTTPS and browsers block it from calling a local plain-HTTP Supabase server. Use the locally served app with the local Supabase stack.

To stop the local stack while preserving its data:

```bash
npx --yes supabase@latest stop
```

`db reset` deletes local database contents and rebuilds the schema. It is appropriate for local development, not a linked production project.

## Optional build-time defaults

Entering the endpoint in Settings is enough. If you build your own copy and want the URL/key prefilled, copy `.env.example` to `.env.local` and set:

```dotenv
VITE_SUPABASE_URL=https://your-project.supabase.co
VITE_SUPABASE_ANON_KEY=sb_publishable_your-public-key
```

The historical environment-variable name `VITE_SUPABASE_ANON_KEY` accepts either a current publishable key or legacy anon key.

For GitHub Pages, create repository **Actions variables** named `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`, then rerun the Pages workflow. These values are public and will be present in the built JavaScript. Never configure a secret or service-role key there.

For a custom origin, keep HTTPS enabled, add the origin under Supabase Authentication URL Configuration, and ensure the app's Content Security Policy allows the HTTPS Supabase endpoint.

## Confirm that sync is safe and working

Complete these checks before trusting the setup with important data:

- Both database tables exist and show Row Level Security as enabled.
- The `encrypted-attachments` bucket exists and is private.
- The included pgTAP test reports eight passing checks when using the CLI.
- Creating and syncing a harmless note reports **Up to date**.
- A second browser/device signed into the same account and vault can retrieve the note.
- Supabase Table Editor shows an encrypted JSON payload, not the readable test note.
- A downloaded Storage object does not contain a readable filename or attachment content.
- A second test account cannot see the first account's rows or Storage objects.

## Troubleshooting

### “Account created. Check your email…”

This is normal when Confirm email is enabled. Open the Supabase confirmation email, click its link, return to Need This Later, choose **Sign in**, and use the same email/account/vault passwords.

### “Invalid API key” or HTTP 401

Copy the Project URL and publishable key again from **Connect** or **Project Settings → API Keys**. Make sure the key belongs to the same project as the URL. Do not use a secret or service-role key.

### Table not found, HTTP 404, or `vault_headers` is missing

The migration was not applied to this project. Complete A2 or run `db push` from B3. Check the linked project reference before applying it.

### RLS error or HTTP 403

Confirm that the account is signed in and that the full migration completed. Do not disable RLS. In Supabase, run the Security Advisor and inspect the policies on `vault_headers`, `encrypted_items`, and `storage.objects`.

### “Sync endpoints must use HTTPS”

Hosted and remote endpoints must begin with `https://`. Plain HTTP is accepted only for `localhost` and `127.0.0.1` during local development.

### Confirmation email opens the wrong address

Update **Authentication → URL Configuration → Site URL** and the allowed redirect list. Hosted projects default to `http://localhost:3000` until you change it.

### The local Supabase stack will not start

Confirm Docker is running and has sufficient memory. Then try:

```bash
npx --yes supabase@latest stop
npx --yes supabase@latest start
```

### Lost vault password or recovery key

The Supabase project owner cannot decrypt the vault for you. If no unlocked device, vault password, or recovery key remains, the encrypted content may be unrecoverable.

## Backups and operations

Supabase database and Storage backups contain ciphertext but still expose metadata and must remain private. Retain `vault_headers` with the encrypted rows; losing a header prevents password/recovery-key unwrapping. Do not log request bodies or authorization headers. Monitor authentication abuse, keep Supabase and the CLI updated, review Security Advisor findings, and retain tested backups before database maintenance.
